# Личный кабинет: первый этап

## Что работает без покупки VPS и базы данных

Личный кабинет — `account.html`, интерфейс — `account.js` и `account.css`. Уже существующий Cloudflare Worker проверяет подпись Telegram и выдаёт короткую подписанную сессию. Новых секретов не требуется: используется существующий `TELEGRAM_BOT_TOKEN`. Код проверки находится в `backend/account.mjs`; сборка `node scripts/build-worker.mjs` включает его в единственный файл `deploy/worker.mjs`.

Профиль не принимается из localStorage как подтверждённая личность. Вход через виджет проверяется HMAC-SHA256 с ключом SHA-256 от токена бота, вход через Mini App — по алгоритму WebAppData. Проверяются подпись, возраст подтверждения, Telegram ID. Сессия ограничена одним часом, подписана отдельным ключом назначения и привязана к URL сайта. API принимает браузерные запросы только с настроенного origin. Токен бота в браузер не передаётся.

## Вход внутри Telegram

В боте есть кнопка **«Личный кабинет»**. Ссылка `https://t.me/DeviceWorkshop_bot?start=account` помещает её первой в ответе бота. Страница открывается как Mini App; SDK передаёт initData, сервер проверяет его и показывает профиль. Пароль и покупка сервера не нужны. Существующая кнопка каталога остаётся доступной.

## Вход из обычного браузера

В кабинете есть официальная кнопка Telegram Login Widget. Для её работы владелец должен один раз связать домен с ботом в **@BotFather → `/setdomain` → @DeviceWorkshop_bot**. Указать только:

```text
trofimmokrov-netizen.github.io
```

Без `https://` и без `/TigranSite`. Настройка кнопки меню Mini App сама по себе не устанавливает домен виджета. Выполнить `/setdomain` через публичный Bot API нельзя; это действие владельца в BotFather. До его выполнения доступен вход внутри Telegram через кнопку бота. Не включать виджет на чужом домене и не подменять эту проверку локальным профилем.

## Черновики

Пока нет общей базы данных. Пользователь сохраняет до 20 черновиков в localStorage текущего браузера с ключом своего проверенного Telegram ID. Доступны редактирование, удаление с отменой, подготовка и копирование сообщения мастеру. Черновики не помечаются как отправленные заявки, не синхронизируются и не являются записью на ремонт. Сообщение пользователь отправляет самостоятельно в @DeviceWorkshop.

Сессия хранится в sessionStorage, не в URL. Выход очищает её в текущей вкладке; подписанный токен не отзывается в базе, которой пока нет, и истекает через час. Для следующего этапа с постоянной историей, отзывом сессий и статусами ремонта можно подключить Cloudflare D1/KV и определить реквизиты оператора, сроки хранения и доступ мастера. Данные существующих локальных черновиков не следует переносить на сервер без явного действия пользователя.

## Обновление и проверка

1. `node backend/account.test.mjs` — подписи, подмена данных, срок действия, привязка сессии и CORS.
2. `node backend/webhook.test.mjs` — команды, webhook и переход в кабинет.
3. `node scripts/build-worker.mjs` — обновить готовый файл.
4. Push в main публикует сайт через GitHub Pages; связанный Cloudflare Worker обновляется своей сборкой Git-репозитория.
5. В API `/api/account/config` с заголовком Origin сайта должен приходить `auth_enabled: true`. Проверить реальный вход, затем сохранение черновика. Вход настоящим пользователем нельзя считать проверенным только по локальным тестам.
